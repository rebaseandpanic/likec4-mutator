# Test plan: Read and edit LikeC4 views and dynamic view steps

**Date** 2026-10-15 · **Requirements**: `docs/plan/lc4m-15.29/spec.md` · **Plan**: `docs/plan/lc4m-15.29/plan.md`

Every row is a vitest unit test (`npm test`; a focused run is `npx vitest run --maxWorkers=2 <files>`). The project has no other test level: integration, e2e, smoke and mutation are not provided, so no row uses them. Every row runs in `wave`. The only approved check that reads code is the coverage-table check inside `npm run lint`. It is a gate, not a row (see "Not unit-tested").

Row numbers are stable across critique rounds:
- Rows 34 and 35 moved to "Test infrastructure" as gates I-4 and I-5 (round 1, F2). Their numbers are not reused.
- New rows are appended: 94 (D43), then 95–96 (round 1, F7).

**Expected values** come from four places:
- LikeC4 1.59.4 itself, through the T002 oracle in `tests/helpers/likec4-model.ts`:
  - `parsedViews` (per-document `c4Views`, before `extends` resolution);
  - the computed views (`_type`, nodes, edges, step sequence), exposed through the separate computed-view accessor of T002;
  - `linkedViewReferences`;
  - `validateLikeC4` / `expectValidLikeC4`;
  - the comparison helpers `expectRulesAgreeWithLikeC4`, `expectStepsAgreeWithLikeC4`, `expectViewsAgreeWithLikeC4` and `expectComputedViewsSurvive`.
- The literal LikeC4 outputs recorded in spikes 02–05 and in the probes of tests-rationale R-3.
- The spec text: D37 examples, D27/D41 file order, D36 forms, D43.
- The input text of the test itself: positions, written forms, and the hand-written expected text of a view, which is fed to the oracle.

No expected value comes from the library's own output.

**Column "Waits for code".** It lists the plan tasks whose code the row exercises. The **last** id is the anchor: the task that creates the row's test file, and into which the row is embedded. Earlier ids are tasks whose code the row exercises through the anchor (for example `T010, T015`: the rule check of T010 reached through `addView` of T015; `T004, T005, T006`: index and resolver exercised by the T006 test task). In build order every earlier id comes before the anchor.

**Conventions used in the rows:**
- **BI (byte-identical rejection):** the call throws `InvalidWriteError` with the named `field`. `serialize()` before equals `serialize()` after. `listViews()` before equals `listViews()` after (INV-2, no in-memory change).
- **ADDR (INV-3 view selector):** each of these is rejected on `id` with BI:
  - an unknown id;
  - an id declared in two files;
  - LikeC4's generated id of an unnamed view, taken from the oracle's computed views.
- **SURV:** `expectComputedViewsSurvive(before, after[, removedId])` passes. Every named view LikeC4 computed before the write, except the one `removeView` removes on purpose, is still computed after it. Generated and unnamed views are exempt (INV-9, SC-004).
- **LINK:** checks INV-8 using `linkedViewReferences`, taken before and after the write.
  - Every reference occurrence that LikeC4 **resolved before** the write is enumerated, unless it lies inside text the write edits or removes on purpose (the edited rule or step, the removed declaration).
  - Each such occurrence must still be linked **to the same target** after the write.
  - Both a re-targeted reference and a resolved-to-unresolved reference fail the check.
  - Occurrences are matched across the write by referrer view id, role, written text and ordinal among equal texts, so a move does not break the matching.
  - References that were unresolved before carry no obligation. Row 56 additionally requires named unresolved references to become resolved.
- **CMP (computed nodes):**
  - The test writes by hand the text the view should have after the write.
  - The nodes LikeC4 computes for that hand-written workspace are compared with the nodes LikeC4 computes for the library's output, for the edited view.
  - Neither side is the library's own reading.
- **SEQ (step sequence):**
  - The expected sequence is LikeC4's computed sequence **before** the write, transformed as the spec says: insert at a position, patch in place, reorder per D37, regroup into `par`, drop, or leave unchanged for a dynamic rule write.
  - The actual sequence is LikeC4's computed sequence **after** the write, for the **whole** edited view.
  - Both are compared by content: source, target, title, kind, backward flag and `par` grouping. Positional ids are not compared (FOR-PLAN 8).
- **Untouched (INV-5):** the text before and after the edited range is byte-equal to the input. The range is computed in the test from the literal it wrote.

**Scope of the accepted-write obligations: feature writes.** A **feature write** is a successful call of one of these operations of this feature:
- `addView` (new and existing options), `updateView`, `removeView`;
- `addViewRule`, `replaceViewRule`, `removeViewRule`;
- `addViewStep`, `updateViewStep`, `moveViewStep`, `removeViewStep`, `addViewParallel`;
- the `apply` forms of all of the above.

**Legacy regression calls are outside this scope.** Existing operations are called in rows 36–40, 42, 47 and 93: `addElement`, `addRelationship`, deployment writers, and existing `apply` operations. Those calls keep only their own assertions, as written in the unchanged test files and in each row.

Row 47 in particular keeps its accepted `addElement` and its observation that a view reference becomes unresolved. It **does not** get LINK, SURV or Wv: making that reference unresolved is the pre-existing behaviour INV-7 preserves (RES-plan-1).

Row 41 rewrites three `addView` tests. `addView` is a feature write, so row 41 is in scope.

- **Accepted feature writes — a matrix-wide convention.** **Every** successful feature write in every row inherits the obligations below. That includes accepted counterparts inside rejection rows, each accepted branch of a table, each successful mutation of an `apply` run, and no-op branches. A row cannot opt out.
  - **Wv (valid input):** the output passes `expectValidLikeC4` (INV-1, SC-003); every declared view reads back equal to the oracle through `expectViewsAgreeWithLikeC4` (INV-4 on the result); SURV; LINK.
  - **Wi (input that already has LikeC4 errors):**
    - the written values read back as requested;
    - LikeC4's error multiset after the write equals the one before. Errors are compared as `<file>: <message>` with line numbers dropped. A row that expects named errors to disappear compares with "before minus exactly those errors".
    - SURV and LINK, as on a valid input.
    - Old errors may remain (INV-1 introduced-only). Survivors are not compared field by field, because LikeC4's model of an invalid input is best effort.
    - Precedent: `tests/mutator/semantic-write-checks.test.ts` ("adds no error").
  - **EFF (computed effect, SC-004):** every successful feature **rule** or **step** write must show its computed effect against an expectation derived independently of the library:
    - **Rule writes** (`addViewRule`, `replaceViewRule`, `removeViewRule`, and `addView` with `includes`):
      - on element and deployment views → **CMP**;
      - on dynamic views → **CMP and SEQ**. The expected sequence is the sequence before the write: a rule write must not reorder, add or drop steps.
    - **Step writes** (`addViewStep`, `updateViewStep`, `moveViewStep`, `removeViewStep`, `addViewParallel`) → **SEQ** over the whole view.
    - This includes the accepted counterparts of rejection rows and the `apply` branches (rows 89, 91).
    - A row's own effect assertion (read-back, an extra OP, Untouched) comes in addition.
  - **No-op branches** (row 82): the result is byte-identical, `serialize()` before equals after. That implies Wv and EFF for an input already shown valid by P. `changedFiles` is empty.
  - **`apply` successes** (rows 89–92): Wv and EFF are applied to the output files, with `before` = the input copy.
- **2F (both fixtures):** the row runs on `tests/fixtures/views-catalog/` and on `tests/fixtures/views-flows/` (T001), with each fixture's own names.
- **P (preconditions first):** before its loop, a 2F row asserts that the fixture passes `expectValidLikeC4` and that every construct the row iterates is present in `parsedViews`. Non-emptiness is asserted before the loop.
- **OP (oracle precondition):** an oracle fact the row relies on is asserted inside the row. Examples: a bodyless view is absent from LikeC4's views; a block-level style is prepended; a `par` that contributes no step is absent. The helper has no test of its own.

Every row with an accepted **feature** write therefore needs the T002 oracle. Its "Needed to run" names `tests/helpers/likec4-model.ts` (T002). Legacy regression rows (36–40, 42, 93) do not, unless they say so.

**Fixture blind spots (apply to every 2F row):**
- Both fixtures are valid and use the default project (no `implicitViews`, no `likec4.config.json`). They have no syntax errors, no duplicate view ids and no ambiguous names. One file is CRLF.
- The library parses each file standalone without linking, while the oracle links. A form absent from the fixtures is not exercised by them.
- These cases are therefore inline in the rows that need them:
  - LikeC4-invalid inputs: a stray `if`, a parent–child step, a chain after a backward step, a duplicate id, unresolved references;
  - syntax errors;
  - ambiguity;
  - unsafe input;
  - one-line bodies;
  - the `try` / `alt` contribution classes.
