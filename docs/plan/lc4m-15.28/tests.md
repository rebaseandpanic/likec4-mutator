# Test plan: Read and edit the LikeC4 deployment model

**Date** 2026-10-12 · **Requirements**: `docs/plan/lc4m-15.28/spec.md` · **Plan**: `docs/plan/lc4m-15.28/plan.md`

All product rows are vitest unit tests (`npm test`); the project has no other test level. Every row runs in `wave`.

Row numbers from round 1 are kept so the critiques can cross-reference them:
- Rows 1–5 and 37 are in "Test infrastructure and review evidence".
- Rows 33–35 are merged into row 32.
- New rows start at 83.

**Expected values** come from three places:
- LikeC4 1.59.4 itself: `buildLikeC4Model` (`$data` layer and getters), the new `linkedReferences`, and `validateLikeC4` / `expectValidLikeC4`.
- The literal outputs recorded in spikes 02–07.
- The spec text, or the input text of the test itself (positions, declarations).

No expected value comes from the library's own output.

**Conventions used in the rows:**
- **BI (byte-identical):** `serialize()` before equals after, and a read of the addressed entity returns its earlier value (INV-2).
- **Wv (accepted write on a valid input):**
  - every node, instance and deployment relationship still in the workspace is compared field by field with the oracle through `expectDeploymentNodesAgreeWithLikeC4`, `expectDeploymentInstancesAgreeWithLikeC4` and `expectDeploymentRelationshipsAgreeWithLikeC4` (T002), including the D2/D10/D18 exceptions (D18: opacity and non-library icons compared with the written literal, not with LikeC4's computed value);
  - the output passes `expectValidLikeC4` (SC-002, SC-003, INV-1).
- **Wi (accepted write on an input that already has LikeC4 errors: syntax errors or ambiguous references; rows 50, 62(c), 63, 70):**
  - the library reads back every written value as requested;
  - LikeC4's error set after the write equals the set before (rows 50, 63, 70: an unrelated syntax error stays). Exception, row 62(c): the removal is expected to resolve an existing ambiguity, so there the set after the write is a sub-multiset of the set before (errors may disappear, none may appear). The sets are compared as multisets of `<file>: <message>` with line numbers dropped, because the write moves lines. Precedents: `tests/mutator/semantic-write-checks.test.ts` ("adds no error") and `tests/mutator/add-element-references.test.ts`.
  - Old errors may remain (INV-1 introduced-only). No clean validation is required.
  - Blind spot: the surviving entities are not compared with the oracle, because LikeC4's model of an invalid input is best effort.
- **2F (both fixtures):** the row runs on `tests/fixtures/deployment-zones/` and on `tests/fixtures/deployment-clusters/` (T001), with the entity names of each fixture.
- **P (preconditions first):** before its loop, a 2F row asserts that:
  - the fixture passes `expectValidLikeC4`;
  - the constructs the row iterates are present in the oracle's `$data.deployments` (§6: non-emptiness before the loop).
- **OP (oracle preconditions):** the oracle facts a row relies on are asserted inside that product row (rows 7–9, 13, 21, 22). They are not a separate test of the helper.

**Fixture blind spots (apply to every 2F row):**
- Both fixtures are valid, LF-only, free of syntax errors, duplicate ids and ambiguous names, and use the default project (no `likec4.config.json`).
- The library parses each file standalone with `LangiumParser` (no linking), while the oracle links. A reference form that is absent from the fixtures is not exercised by them.
- Invalid, CRLF, ambiguous and unsafe-input cases therefore live inline in the rows that need them (18, 42, 50–51, 57–58, 62–63, 68, 70, 86–92).

### Reference stability (US-12)

**Wiring blind spot (rows 28–31).** These rows call the snapshot directly with supplied texts and removal sets. They stay green if no writer calls the snapshot or passes its removal set. Writer-level coverage is in rows 32, 36, 44, 55, 62, 74 and 93. Each of those rows is one obligation that holds both a changed-target rejection and a safe accepted write, so a missing guard and an always-rejecting guard both go red within the same row (R-5).

Strict-path `extend` targets in the snapshot have no writer-observable effect: no accepted write can re-target them, because same-path additions are duplicate ids (row 45) and target removals cascade (row 52). Row 29 is therefore unit coverage only, and no re-targeting addition is invented.
